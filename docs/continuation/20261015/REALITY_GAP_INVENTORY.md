# Geometry reality gap inventory — 2026-10-15

## Scope and finding

This is a read-only source and document inventory. No geometry, solver, service, CLI, or test was run. It does not promote any existing asset or source qualification.

The current code can make watertight CAD and meshes, and can run a useful native Akantu-to-A12 RGB-D research workflow. It does not yet generate a source-measured everyday or archaeological vessel. Every geometry path inspected is either a fixed analytic demonstration, an analytic family proposal, or a procedural A12 archetype. The existing museum catalog contains useful historical facts and broad dimensions, but no calibrated full profile or scan that binds any generator output to a real object.

The term `geometry_only` or a geometry `PASS` currently means that package and shape checks passed. It is not evidence of an everyday vessel match, archaeological type, or manufacturing method. The current short milestone remains valuable: reuse its two closed native fragments, 158 paired failed facets, and A12 RGB-D adapter as a research/control workflow, while keeping its material qualification `UNCALIBRATED` and its training/production eligibility false.

## How synthetic or analytic assets can reach A12

There are four distinct current paths; keeping them separate avoids overstating the problem:

1. **VF package validation is deliberately geometry-only.** `vesselforge/src/vesselforge/schema.py::validate_asset` verifies `forge.asset.v1`, package paths/hashes, STEP and arrays, face semantics/lineage, and the producer's `geometry_only` report. It does not require a museum/reference ID or compare the exported shape to one. Both the turned toy and hemispherical shell can therefore have a valid geometry `PASS` while remaining analytic candidates.
2. **The VF A12 adapter presently blocks ordinary training export.** `relicweave-synlab/synlab/integrations/forge_asset.py::load_forge_asset` verifies the package and trusts the hash-bound producer report rather than independently measuring geometry. `scene_from_forge_asset` requires explicit preview opt-in for `UNVALIDATED_PROTOTYPE`; its scene says `preview_only=true`, `feature_export_allowed=false`, `production_physical_pass=false`, and `fracture_output/r2_output=NONE`. This is an important existing safeguard. The remaining risk is any downstream consumer treating a geometry-only `PASS`, a preview, or a folder/release name as real-vessel evidence.
3. **A12's “realistic” path qualifies the capture pipeline, not the vessel geometry.** `configs/a12/realistic.yaml` declares `data_scope=SYNTHETIC`; its header says the configuration changes observation/capture settings while preserving the same sampled vessel/material/pattern lineage as the baseline. `synlab.observe.realism::REALISM_RUN_TAG` is specifically `realistic_capture_style`; `realism_tags`/`is_realistic_capture` inspect route, renderer, delivered encoding and realized imaging settings. They do not inspect the mother mesh or a museum/scan source. The companion `docs/a12/realism_gap.md` explicitly describes `photo_mvs` as a real SfM pipeline on synthetic renders and says `REAL_CAPTURE` remains pending. Thus a synthetic or analytic mother can correctly pass a capture-style observation check, but that check cannot qualify it as a realistic vessel. Any exporter, UI or dataset label that collapses those two meanings can overstate shape realism.
4. **The generic A12 generation/export path has no vessel-reality qualification.** `synlab/cli.py::generate` calls `pipeline.run_generation`; `pipeline.build_one_mother` uses `mothers.api.create_mother`, the registered synthetic parametric models, then observations and feature/label/provenance assets. `synlab/storage/export.py::export_training_package` applies view/channel, permissions, closure and truth handling, but no source-reference/profile-match contract. A procedural family can therefore become an ordinary synthetic training sample; QA/release/training-package inclusion is not a finding that its contour matches an everyday or archaeological vessel. `tools/build_demo_assets.py` also calls `sample_parameters`/`create_mother` and initializes its demo split as `train`; its “真实演示” description means outputs come from real module APIs, not real source objects. No literal field named `realisticvessel` was found in the inspected active source. The risk evidenced here is the missing geometry-source eligibility and possible conflation of capture realism with vessel realism, not a proven string-level label bug.

The native Akantu adapter is stricter about its own scope. `native_cohesive.py::validate_native_cohesive_fragments` requires source qualification to identify a preinserted weak seam and uncalibrated material, rejects source claims of physical/pretrain/deployment pass, and its dataset exporter records `SYNTHETIC_SENSOR_RGBD_CLOSED_FRAGMENT_RESEARCH_DATASET`, `RESEARCH_ONLY_UNCALIBRATED`, and all such eligibility flags false. Its two closed components and 158 paired failed facets establish source topology and packet consistency, not vessel typology or real material behavior. Keep this workflow and adapter; use a source-qualified vessel mesh as a future mother when available, and leave the current case as a labeled analytic/control input.

## Main reality gaps

- **No source-measured silhouette.** Current meridians come from constants, simple ratios, or a perfect sphere. The reference catalog has outer dimensions and descriptive text but no complete inside/outside contour.
- **Manufacturing features are generic.** Polyline corners and arbitrary offsets omit sourced rim sections, foot rings, wall transitions, joining bands, local irregularity and separate attachments. The fused round handle is a clean CAD union, not a modeled clay/ceramic joint. The candidate bowl/beaker/jar catalog has no handles, spouts, punched lugs or mold-seam options.
- **Wall declarations are not specimen measurements.** The profile catalog uses radial offsets; the fixed prototype tests a profile offset and one planar floor; the sphere uses a concentric design gap. None is a source-bound global thickness field.
- **Families conflate names with realizations.** “Bowl”, “jar”, “ewer” and “beaker” are broad retrieval labels. Real daily and archaeological examples vary by period, place, material and process; one analytic parameter preset cannot stand for each label.
- **Appearance is a separate unqualified layer.** Procedural paint bands have zero relief and non-calibrated colors; a plausible render cannot make the geometry or style source-authentic. Existing material status stays `UNVALIDATED_PROTOTYPE` / `UNCALIBRATED`.

## Minimum reusable integration and cohort rule

Architectural choice remains with the main agent. The minimum useful pair is:

1. **One geometry producer API in VesselForge.** Make a typed source-bound geometry input the input to a shared `build_components`/solid builder. It must carry the actual measured outer and inner contour (or a scan/mesh-derived equivalent), scale/frame evidence, source reference and explicit unknown regions; the builder must create the actual rim, wall, base/foot and attachments from those coordinates. Rewire `profile_catalog` as a suggestion/control generator only, and converge the independent bowl builder when practical. Do not permit an evidence record or status field to stand in for missing contour geometry. Keep `VesselSpec`, `BowlSpec`, profile defaults and SynLab archetypes available under explicit analytic/synthetic control identities.
2. **One A12 source/eligibility path.** Add a versioned import/qualification path used by both mother creation and `export_training_package`. It should carry the hashed geometry source and geometry-build provenance into A12, keep provenance/answer fields out of observations/features, and assign samples to `REAL_REFERENCE_GEOMETRY`, `ANALYTIC_CONTROL`, or `SYNTHETIC_CONTROL` only after the geometry itself is compared with its reference. Export the two control classes as controls, with their old assets/controls intact; exclude them from any `realistic vessel` cohort. A reference tag with an invented contour must fail the comparison.

`forge.asset.v1` structure and exact native source integration can be reused. Real geometry should replace the analytic mother shape at the input to the native Akantu mesh/fragment workflow; the existing weak-seam experiment, paired surfaces, RGB-D renderer, alignment metadata and uncalibrated-material caveats remain distinct evidence. A contour upgrade cannot upgrade the material or physics qualification.

## Review gates: visual judgment vs automatic geometry checks

**Root/domain visual review is required** for whether a selected daily or archaeological object is represented by the supplied calibrated views/scan; whether the rim, foot, shoulder, handle/spout roots, holes and joining seam match that source; and whether the evidence supports the named family/process. Review must leave unobserved regions marked unknown. The existing catalog descriptions are sufficient for broad semantic review, not exact profile approval. Visual review also cannot turn a procedural render palette into measured material data.

**Automated checks can cover geometric consistency:** source scale and frame transforms; profile/mesh self-intersection and closed material volume; monotone or physically valid wall transitions; independent H/D/mouth/base/foot measurements against source tolerances; sampled cross-section/mesh distance to calibrated source geometry with a stated error bound; global minimum wall analysis; rim/floor thickness; handle/attachment intersection and component connectivity; mesh topology and tessellation; and source-to-triangle lineage through STEP, native meshing and A12 observations. Keep these as geometry checks, separate from human type/authenticity approval and physical/material qualification. The present sampled mesh-to-CAD tolerances and analytic volume checks remain useful lower-level tests, but do not measure source similarity.
