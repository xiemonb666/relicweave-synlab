# RelicWeave Forge implementation ledger (2026-10-03)

## Ownership and release boundary

- VesselForge Core and PG-Frag Core are separate codebases with independent versions, Python APIs, CLIs and CI. A12 remains RelicWeave's observation, degradation, relation/retrieval, pretraining and diagnostics platform.
- Integration starts at the first vertical slice: VF asset → versioned adapter → PG solver → validated result/status back to A12. Independent releases do not require every stage to build a complete web UI, database, or storage system; existing A12 consumers can be reused. Solver processes and A12 API/worker environments stay isolated.
- VF/PG each embed the same neutral schema validator; no fourth shared repo. PG does not import VF or SynLab. Schema changes require the main agent's decision.
- VF owner scope: `ShardForge/vesselforge/**`, `ShardForge/third_party/vesselforge-runtime/**`, `relicweave-synlab/tmp/review_20261003/implementation/vf/**`, and this ledger. PG and SynLab production implementation/configuration belong to their owners.

## forge.asset.v1 contract

- Root: `schema="forge.asset.v1"`, `units={length:"mm",time:"s",mass:"kg"}`, `frame="right_handed_z_up"`.
- `geometry={surface_npz:"geometry/surface.npz", solid_step?: relative package path}`. Surface arrays are `vertices_mm` float[N,3] and `faces` int[F,3].
- `fields={surface_fields_npz:"fields/surface.npz"}`. Fields arrays are `face_region` int[F], `albedo_linear_rgb` float[F,3], `roughness` float[F], and `vertices_material_xyz_mm` float[N,3]. The last is asset-local rest/material position, initially equal to `vertices_mm`; it is for re-evaluating appearance after fragmentation, not a deployable/model feature. A12 feature export must exclude reference coordinates and evaluate appearance for rendering. PG must preserve/interpolate these coordinates only when its mapping supports that operation; unsupported interpolation must remain explicit.
- `material={id, appearance?: optical model/base color/roughness source, mechanics:{rho_kg_m3,E_pa,nu,Gc_j_m2}, calibration_status:"UNVALIDATED_PROTOTYPE", provenance}`. The initial asset has one mechanical material. Appearance and mechanics are separate. `ornament.recipe.material_binding_id` must exactly match `material.id`; a mismatch fails validation. Painting changes optics only.
- `ornament={kind:"painted", recipe:{coordinate_map:"cylindrical_z_up_mm", explicit target region codes, fracture surfaces excluded, ...}}`. This first sample has no geometric relief. Its historical style is `NOT_VALIDATED`; it must not be presented as a verified historical pattern/type.
- `files` lists package-relative `{sha256,bytes}` entries and excludes `manifest.json` to avoid self-hashing. Validators reject absolute paths, traversal and symlink escape. `provenance={producer,version,backend,backend_version,seed,spec}`. `validation={report:relative JSON path,status:PASS/FAIL/PENDING,scope:"geometry_only"}`.
- Same-seed canonical geometry/parameters should reproduce. STEP headers may contain timestamps, so the complete package is not claimed to be bitwise reproducible. `asset_id` is content identity, not geometry or physics acceptance.
- Mechanics numbers are illustrative unvalidated inputs, not measured ceramic properties. Geometry QA does not establish material calibration or physical truth.

## Runtime, evidence and current status

- Resource split: this workstation is for low-face-count local smoke tests, deterministic package/CLI/validator tests, one small CAD example and review renders only. The later RTX 5090 32GB / 48GB machine is for approved batch synthetic generation/training. No batch job is started here. Paths are package-relative or user-provided, not hard-coded to either machine.
- CAD runtime is isolated at `ShardForge/third_party/vesselforge-runtime/venv`. CadQuery 2.8.0/OCP 7.9.3.1.1 installed there; no change to SynLab's venv. Actual `import cadquery` succeeded. One initial revolve+sweep+boolean probe produced valid body, handle and fused object; fused result was one solid/one shell, volume 28165.474948 mm³ and bbox about 53.1×41×56mm. This is a probe, not final asset acceptance. Source was initially at `ShardForge/tmp/review_20261003/implementation/vf/probe_geometry.py`; a copy is being retained under SynLab's designated VF evidence directory. Probe output was not archived as a log, so those values are preliminary reported evidence until reproduced by the packaged CLI.
- Main-agent visual review of older SynLab figures `data/a12_reports/physical_layer/fracture_appearance_materials_1024.png` and `data/a12_reports/physical_layer/fracture_appearance_AB_1024.png` found reality FAIL: procedural stripes/moiré and triangle-face mottling; color-only difference did not demonstrate realistic fracture/surface mechanisms. These are old SynLab images, not VF output; their watertightness or A/B appearance is not physical realism evidence.
- The old `docs/a12/fracture_calibration.md` describes calibration from fitting generator scans; that is not independent real ceramic experiment calibration. Document ambiguity is recorded for its owner; this ledger does not edit that file.
- Candidate visual/data references for later comparison: Fantastic Breaks (https://terascale-all-sensing-research-studio.github.io/FantasticBreaks/) has complete/broken scans, but its repair part is a synthetic proxy; FRACTURA/GARF (https://ai4ce.github.io/GARF/) includes real ceramics and a separate synthetic fracture subset. No large dataset was downloaded. Neither source establishes E/Gc or real fracture mechanics without material experiments. Use only provenance/licence-checked real scans for geometry/surface comparisons; do not label proxy/synthetic examples real.
- Initial accepted feature state: CadQuery/OCP imports and the revolve+sweep boolean probe runs. The deliverable is still an unvalidated prototype until package generation, numeric tests, actual surface/cut/joint renders and independent visual review complete. A geometry PASS is not historic-style or physics PASS.
