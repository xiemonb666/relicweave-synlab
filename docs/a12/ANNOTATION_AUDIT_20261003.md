# RelicWeave V1.44 标注与真值边界审计（2026-10-03）

## 结论

当前能确认的是：VesselForge 产出了可复核的合成 CAD 几何包；PG-Frag 产出了一个均匀梁 OSB 端点 bond-state fixture 和一个未断裂 wheel smoke；A12 导出了大体完整、可校验的合成训练包，并含有自己的合成断裂面与关系标签。这些证据支持几何/序列化/合成流程实验，**不支持将数据描述为经真实材料标定的物理数据集，也不支持用 PG-Frag 代替 A3/A4 的真实邻片检索、拒绝补采或 STOP 判定**。

当前 A12 有两个不同结论，必须分开看：直连资产 API 的 feature-array 和 metadata projection 有显式 allowlist，测试也覆盖了 ancestry 隐藏；但实际 `training_package/deploy` 出口仍暴露原始 fragment、lineage、mother 名称、R2 mate 数量及多个原始 ID 索引。该问题是 deploy 包的可见元数据/身份边界失败。审计**没有**证据证明这些字段已经被拼入模型的数值 feature vector；已检查的训练 smoke 只用 query ID 构造特征行，数值 feature 由 observation/geometry/token shards 装配，关系监督另从 research view 读取。

标记语义：`PRESENT` 表示当前制品里实有数据；`SUPPORTED` 表示当前程序/契约明确支持且有相应证据；`UNKNOWN` 是未验证；`UNSUPPORTED` 是明确不实现；`NOT_TESTED` 是没有对应测试；`FAIL` 是已测边界不满足。缺失不能自动解释为 negative，`UNKNOWN` 不能当作“确认不存在”。

### 契约结构与数值/真实校准分层

PG job schema 顶层 `additionalProperties=false`，只列均匀盒梁或 `forge_asset_surface` 两种 initial-condition 结构，并强制材料状态为 `UNVALIDATED_PROTOTYPE`；这证明请求形状被声明，不证明表面体积离散化已经实现。result schema 只强约束少量顶层字段，`units/initial_condition/material/solver/state/validation` 等子对象是通用 `object`，因此 bond/point 数值一致性要以 backend runtime validator 和实际 CSV/result 为证据。backend 的 `validation.status=PASS` scope 也明确限于 bounded endpoint serialization/process completion。精确来源：`pgfrag/schemas/pgfrag.job.schema.json:6-88`、`pgfrag/schemas/pgfrag.result.schema.json:6-25`、`pgfrag/src/pgfrag/backend.py:262-443,659-686`。

A12 的 direct asset API feature projection、A12 training-package export 和 package-reader 是三个不同表面：API allowlist 的测试通过不能证明另一个 package serializer 的 query roster/index 隔离安全；package hash 验证也只说明导出文件与 manifest 一致。相同地，VF `forge.asset.v1` schema/geometry report 的 PASS 不覆盖 PG 实际接入、A12 真物采集或外部材料校准。

## 当前部署边界实测

A12 manifest 的 `separation.answer_field_scan.hits=[]` 和 `features_carry_answer_fields=false` 只反映 exact-name scan。实际 queries.parquet 含 77 条，lineage 14 个、mother 16 个、fragment 77 个、query_id 77 个、`historical_N_G` 目前出现 0/1；首两行 R2 query 的 cardinality=1。`deploy/obs/index.json`、`deploy/geometry/index.json`、`deploy/tokens/index.json` 与 `deploy/deploy_index.json` 也以原始 fragment ID 作 map key。不得将这些原始名称称为 opaque。另一方面，独立扫到的唯一 exact forbidden key `level` 来自 Zarr v3 的 `zarr.json` 存储元数据，不是 degradation 级别泄漏；新检查应按容器/Schema 位置处理，避免把 Zarr 元数据误判为模型答案。

`viewframes.py:215` 在 renderer 侧存在 `object_pose_T_WO` 元数据；但当前已导出的 deploy arrays/metadata inventory 没有实际 pose matrix、VF rest coordinate 或 recipe/seed。部署 channel allowlist 只包括政策声明的视图通道；`frame_id_source="T_WC+K+depth_z"` 记录来源字符串，不含矩阵值。这个结论限于已核验的当前 package bytes，不能自动覆盖未来的新导出器或其他 consumer。

## 最小版本化契约建议（供主代理决策）

1. 新增严格的 A12 deployment package 版本（建议 `synlab.training_package.v2`），把 opaque fragment key 用在 query rows、obs/geometry/token indexes 和 shard member names 的所有关联处；原始 fragment/mother/lineage→opaque map 仅置于 research side。deploy query schema 不允许 `lineage/mother/fragment/historical_N_G/split/parent/event/seed/recipe/pose` 等语义别名。当前 v1 package 应由严格 consumer 明确识别为 legacy/untrusted，避免仅凭 manifest hash 即默认安全加载。
2. 每个数据/标签都保留独立 `source_kind`、`source_ref/hash`、producer/schema version、unit/frame、ancestry group 的研究侧引用和显式状态（PRESENT/UNKNOWN/UNSUPPORTED/NOT_TESTED/INVALID）。缺字段不能被填成 0、false、negative 或 `PASS`；历史 R2、合成 R2、bond adjacency、positive-area surfaces 不共用同一语义标签。
3. PG 下一版 result contract（若实现，再升 `pgfrag.result.v2`）应把 input source kind/hash、离散化/表面对应、原生 bonds、endpoint state 与 event timeline 分开建模。直到 VF-volume discretization、正面积双侧裂面及其 ancestry/event lineage、材料标定和对应 QA 有数值证据，PG 不能发出可供 A3/A4 的 historic-R2 或 STOP 标签。
4. split contract 按 mother/lineage group 分割；raw group key 留 research view，训练/部署只用 opaque key。冻结 gate 必须在所有 required gates 通过后才允许把 package 标为可用；“export OK”“hash OK”“geometry PASS”各自不得替代冻结或 real-world calibration。

此建议没有改动现有 schema、data package 或生产 API；由主代理决定是否扩展和版本号。
