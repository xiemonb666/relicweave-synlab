## Blocking finding

The execution receipt cannot pass the frozen postverify helper’s push-result gate. The executor records the per-repository command result as `push_returncode` (including at `execute_closeout_backup.py:1014`; resume handling reads the same key at `:986`). The helper reads only `push_exit_code`, `push_rc`, or `push_command.rc` (`independent_postverify_all_code_backup_20261007.py:878–883`). The executor writes none of those accepted fields. Thus even a successful push with `push_returncode: 0` is rejected as “lacks successful push rc.” Align the names or teach the frozen helper to accept the exact executor field before authorizing execution.

## Other source-level risks requiring resolution or explicit acceptance

- **Git command failures are not consistently fail-closed.** `GitRunner.run` records each return code, but `read_repo_state` parses stdout directly from `ls-tree`, `ls-files`, and `diff` at `execute_closeout_backup.py:655–658`; `stage_expected` similarly parses `diff` and index output at `:895–902` without first checking each return code. An error can be interpreted as an empty pathset/tree. Other later checks often stop the operation, but the executor can already have staged files, and a zero-delta path can be misreported as clean. Check every read-only Git command’s `returncode` before parsing and before treating empty output as a valid state.
- **Attribute-sensitive tracked edits can conflict with exact raw-blob staging.** The builder creates an original-source action for a tracked modified path, and separately adds a raw snapshot whenever the worktree raw blob differs from HEAD (`make_entry`, around lines 245–293). The original row remains eligible in `actions` (line 531). If that original destination has `text`, `eol`, or `filter` attributes, the builder’s `-text` rule only protects the raw snapshot path; the executor still expects the original path’s Git blob to equal the raw worktree SHA-256 blob. Git may normalize the original file on `add`, so the exact staged-path/blob gates can fail after other paths were staged. This is conditional on the final inventory’s per-path attributes; check those rows before GO or exclude the original-path change when the raw snapshot is the intended recovery target.
- **The builder ignores `check-attr` failure.** It stores `rc_attr` from `git check-attr` but does not require `rc_attr == 0` before using an empty `attrmap` as “no relevant attributes” (`build_closeout_inventory_v2.py:407–419`). A failed attribute query can therefore suppress raw-byte handling. Fail the inventory closed on nonzero status or malformed/incomplete attribute output.
- **Supplementary-source symlink check is bypassable.** Supplementary `source_absolute` is set using `.resolve()` at `execute_closeout_backup.py:531`; later `path_has_symlink_component` checks that already-resolved path (`:561–564`). A symlink in the approved workspace-relative source path is therefore hidden from the component check. Preserve the unresolved root-relative path through validation, as the main manifest rows do.
- **Git provenance is recorded, but not fully pinned across tools.** The executor uses an absolute bundled Git path and records its file size/hash in the receipt. The current bundled binary is 46,464 B, SHA-256 `c53279919fdea03474bb23b465b3a82287157491f1bd69a5eb82dd9831582333`. The builder invokes `git` through PATH (currently `C:\Program Files\Git\cmd\git.exe`) and records no Git binary pin; the postverify helper defaults to PATH unless `--git` is supplied. If the review requires one authoritative Git implementation end-to-end, pass the bundled path to verification and bind the expected executable hash to the approved execution inputs; the executor currently only records whatever bytes are at its hard-coded path when it runs.

## Coverage decisions

The frozen builder includes the three selected NPZ paths explicitly. All three files are present and under the executor’s 20 MiB selected-data cap: the moving-front failure cache (1,770,008 B), tip-aligned quadrature cache (12,356,515 B), and mixed93 saved cache (1,569,232 B). Source snapshots with code-like suffixes such as `.py.snapshot` and `.py.pre...` are recognized; documentation, frozen root documents, exact raw snapshots, and small stable `tmp/backup_coordinator` records are eligible under explicit rules. The generated README is now pinned before scanning; the builder checks that the pre-scan bytes match its scanned inventory row and checks again after scanning, without rewriting README later. The 5 MiB stable-record threshold is consistent between the builder constant and its inventory note.

Two classification edges remain visible in source. First, `SECRET_RE` excludes every `.env.*` file, including a harmless `.env.example` template; no `.env.example` or `.env.sample` file was found in the three repositories in the narrow filename check, so this is a policy defect without a current discovered candidate. Second, XML is only included when under a `CLOSED` root. The repository contains two `junit_portable_fixture.xml` paths outside those roots, and the docs-evidence copy is referenced by the validation summary and backup evidence index. If that JUnit evidence is part of the required stable record set, the current rules omit it; classify that exact fixture/evidence explicitly or record the exclusion decision. JSON under tests/fixtures is checked before the broad generated-output rule, so a `tests/.../output/...expected.json` fixture is retained by the current ordering.

## Confirmed controls

- Execution requires the exact main manifest SHA for both `--approved-sha256` and `--root-go-confirmed`; execution also requires a separately SHA-pinned supplementary manifest and a matching supplementary GO SHA (`execute_closeout_backup.py:461–538`).
- The supplementary manifest must contain exactly the three fixed role/source/destination tuples for coverage, source map, and frozen control copy (`:102–106`, `:502–515`). The approved-action and add/staged/changed pathsets are stored per repository. `git add` uses explicit literal pathspecs after `--`, with `--force` only for exact pinned ignored paths; pushes are normal, non-force pushes to the fixed branch.
- The executor applies `core.autocrlf=false` per command, checks repository root, branch, origin, parent, remote state, and exact source/destination SHA-256 and Git blob IDs. It records the bundled Git executable’s actual size and SHA-256. Logs are saved through the configured high-confidence credential redactor; the raw command output itself is represented in the receipt by byte counts and hashes.

The source-only review does not establish that a final inventory has complete coverage or that any Git mutation succeeded. The executor/helper receipt mismatch is sufficient to keep the frozen candidate blocked.
